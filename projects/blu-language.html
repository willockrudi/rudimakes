Blu - A Compiled Programming Language 🛠 In Progress

A compiled programming language built from scratch, for no reason other than finding out whether I could. Full pipeline from lexer to native x86-64 codegen, running on Linux, with closures, record types inferred from usage, a standard library, and 400+ regression tests that have to stay green.

compiler language c++ x86 linux from-scratch

Technical Notes

Why

No practical reason. I wanted to find out whether I could build a real one - not a toy interpreter, but something with a full pipeline that emits native code and can be held to the same standards as a tool you would actually use.
Blu compiles to native x86-64 assembly and runs on Linux. The compiler is written in C++.

The Pipeline

Five stages: lexer, parser, semantic analyzer, IR, x86-64 codegen.
The order they were built in matters. Lexer first, made deterministic before anything depended on it. Parser next. Then semantic analysis - undefined variables, wrong argument counts, duplicate declarations - which is the layer nobody notices until it is missing and errors start surfacing as bad codegen instead of as compile errors.

Language Design

Semantics were frozen early, before the standard library went in, so the language could not drift while it was being built on.
Records are called forms, and their field types are inferred from usage across the call graph rather than declared. The keywords are give for return, show for print, and when for if.
The standard library covers JSON, CSV, binary encoding, key-value arrays used as databases, process spawning, and environment variables.

Regression Infrastructure

The test suite is the thing keeping the project honest. Several hundred regression tests organized by category, run by shell scripts that report pass rates, now past 400.
The rule is that nothing lands until every test is green. On a compiler this is not optional - a change to codegen can silently break a language feature three layers away, and without the suite you find out weeks later in a program that used to work.

Closures, and a Build That Would Not Link

Closures and forms went in together. Closures meant environment objects, closure allocation, and a new family of IR instructions to capture variables across stack frames. Forms meant inferring field types from how they were used across the whole call graph.
Partway in, the build collapsed into a cascade of errors that pointed everywhere and nowhere. The cause was not in the new code: #include directives had been placed after the opening brace of namespace blu, so the entire standard library had been pulled inside the namespace. Every symbol resolved to the wrong place.
By the time it was found, ir_builder.cpp had accumulated duplicate function bodies and orphaned copy-paste blocks from working around symptoms of it. Rewriting the file from scratch was faster than untangling it. Each fix exposed the next one; individually all of them were small.
Forms edge cases finished at 113/113, closure regression at 10/10.

File I/O

Blu could not touch the filesystem, which put a ceiling on what could be written in it. file.read, file.write, file.append, and file.exists: four C symbols, four arity checks, four codegen entries.
The verification program wrote a file, read it back, and confirmed it existed - which is the first point at which a Blu program could do something that outlived its own process.

What Is Left

Plenty. A map type, a garbage collector, line numbers in error messages, a formatter, a REPL, a module system, a C FFI bridge, and a platform layer.
It compiles and the tests pass, which is a long way from done.
